# Limitations of the current embedded C/C++ runtime

Static analysis of the CMSIS port and pinned Lean **4.35.0**, commit `eb6cafb7290e8bd5f2937522d8d804f58f02bafc`. This report concerns runtime implementation and build dependencies. Standard-library implementations remain unmodified; libc constraints and compiler-specific library selection are documented separately below. Only this document was changed; no firmware was rebuilt or executed. Benefits are potential improvements, not measured savings.

The most significant real-time limitations are **IRQ-masked TLS work, synchronization without guaranteed progress across priorities, and scheduler resource growth without a hard bound**. IRQ-masked libc operations are recorded separately as an external-library integration constraint. For footprint, RTTI, retained initialization dependencies, C++ support and allocator metadata are concrete targets. The port already removes iostreams, excludes desktop IO dependencies, uses `-Os`, and enables function/data section garbage collection.

## Proposals ranked by regression risk

Risk describes the validation needed to trust the proposed implementation change, independently of the severity of the limitation:

- **Low:** localized implementation change; focused regression checks.
- **Moderate:** both toolchains/profiles and targeted compatibility or boundary tests.
- **High:** concurrency, ABI, exhaustion, long-duration or hardware latency testing.
- **Very high:** changes to runtime semantics, ownership or supported capabilities; broad differential testing.

Source keys refer to the implementation references below.

### Low

| # | Current runtime limitation | Proposed runtime change and benefit | Tests needed |
| --- | --- | --- | --- |
| 1 | **Embedded exception messages still contain desktop tooling instructions.** Prepared stack/memory exceptions construct `std::string` messages, including elaboration-stack/Lake guidance and a manual URL. These consume ROM when retained and allocate while reporting resource failure. [B, F] | Replace these messages with short embedded-specific diagnostics or static messages where the exception representation permits. Reduces retained strings and construction work. | Exception type/`what()` behavior and message lifetime; confirm which strings survive linking. |

### Moderate

| # | Current runtime limitation | Proposed runtime change and benefit | Tests needed |
| --- | --- | --- | --- |
| 2 | **RTTI remains enabled without an identified explicit runtime consumer.** Neither toolchain requests `-fno-rtti`; no explicit `dynamic_cast`/`typeid` use was found in the inspected runtime, headers, utilities or adapters. [A, F] | Compile the controlled C++ runtime without RTTI, initially retaining exceptions. Potential ROM reduction; exception-matching type information and virtual dispatch remain. | Both compilers, typed/base exception catches, STL interfaces and C++ FFI class compatibility. |
| 3 | **Cross-file runtime optimization stops at ordinary compilation boundaries.** No LTO is configured, although generated C calls many small runtime helpers. [A, G] | Enable compatible LTO for runtime/generated C and final linking. Potentially removes helper calls and unreachable implementation branches beyond existing section garbage collection. | Full functional profiles; startup, assembly/TLS/retargeting entry points and FFI callbacks; footprint and cycle comparison. |
| 4 | **Core initialization retains optional synchronization implementations.** `lean_initialize_runtime_module()` always calls `initialize_mutex()`, which registers mutex, recursive-mutex, condition-variable and shared-mutex external classes. Their finalizer references retain implementations even when those Lean APIs are unused. The registry itself allocates a vector and mutex. [C, E, F] | Register optional classes on first construction, or separate feature initialization from core initialization. Reduces mandatory runtime dependencies and startup allocations. | Each primitive's first use, concurrent first use, finalization and external-class identity. |
| 5 | **Multiprecision routines have large fixed scratch frames even for small operands.** The non-GMP backend uses `buffer<mpn_digit, 256>`; division/remainder instantiate two buffers. Prepared decimal conversion uses `buffer<char, 1024>`. [B, G] | Use smaller configurable inline capacities or reusable per-thread scratch storage. Reduces runtime stack demand; the heap-versus-stack tradeoff needs measurement. | Arithmetic/sign/aliasing regressions and operand sizes around capacity transitions; concurrent/reentrant calls for reusable scratch. |
| 6 | **The monotonic clock is not self-maintaining across missed wraps.** `cmsis_clock::now()` extends a 32-bit count only when called: a gap of a full wrap loses elapsed time. It also performs 64-bit tick-to-nanosecond conversion despite tick resolution. [D] | Maintain the extended epoch independently of callers; add a direct tick/millisecond fast path while preserving existing API semantics. Improves uptime correctness and reduces conversion work. | Wrap and missed-wrap simulation, frequency scaling, monotonicity and concurrent sampling. |
| 7 | **Runtime initialization can expose partial state.** `lean_initialize_runtime_module()` uses an unsynchronized boolean and sets it before initializing subsystems; a concurrent caller can return while initialization is incomplete. [C] | Use a completion-publishing once state with a defined initialization-failure state. Makes initialization safe for concurrent entry. | Concurrent first calls, reentry and injected initialization failure. |

### High

| # | Current runtime limitation | Proposed runtime change and benefit | Tests needed |
| --- | --- | --- | --- |
| 8 | **TLS access has linear searches inside an IRQ-masked region.** Each emulated TLS access scans the thread list and that thread's descriptor list; first access allocates metadata and storage under the mask. Cleanup frees the entire list while masked. Clang native libc TLS also uses the registry. [C] | Store thread state in a direct RTOS-associated slot and index descriptors; separate allocation/reclamation from short publication sections. Faster steady-state TLS and shorter masked intervals. | Descriptor ABI, alignment/initial values, exception globals, thread-ID reuse and native TLS calling convention with both compilers. |
| 9 | **A condition-variable wait allocates an RTX semaphore each time.** Wait completion deletes it; broadcasts release every queued semaphore under the condition-variable mutex. Wait cost and failure depend on RTX object availability. [D] | Reuse per-thread waiter objects/semaphores or a bounded waiter pool. Removes object allocation from the normal wait path and makes resource demand explicit. | Enrollment/notification races, broadcast, repeated waits, teardown and pool exhaustion. |
| 10 | **Some synchronization can prevent its own producer from running.** Shared-reference get/take/swap loops spin without blocking. Thunk forcing and the patched once lock yield, which does not make a lower-priority owner runnable ahead of a higher-priority waiter. [B, D, E] | Replace retry-only waiting with scheduler-aware blocking or an appropriate short atomic protocol. Restores progress across priorities and avoids continuous retry overhead. | Forced preemption during reference ownership transfer and thunk/once initialization; mixed-priority contention, memory ordering and ownership checks. |
| 11 | **Task-manager resource demand has no configured hard bound.** Queues use growing `std::deque`s; dedicated work creates threads; a pooled worker waiting in `Task.get` increases `m_max_std_workers` and can spawn another worker. Worker creation also allocates `std::function`/wrapper state. [D, E, F] | Introduce bounded queues, pooled worker-start records and resource admission with a dependency-aware nested-wait strategy. Makes memory/thread demand predictable and reduces scheduler allocation overhead. | Nested dependencies, map/bind, dedicated tasks, promises, cancellation, shutdown and exhaustion. A simple worker cap is insufficient because nested waits can deadlock. |
| 12 | **Lean task priority is not an RTX scheduling priority.** Every runtime-created worker uses `osPriorityNormal`. Lean priority controls queue selection or dedicated-worker creation; it supplies neither an OS priority mapping nor a deadline-aware task wait. [D, E] | Add explicit runtime scheduling/worker-priority policy and, if required, timed task waits. Enables integration with application RTOS priorities and explicit blocking limits. | Mixed-priority execution, nested waits, dependency inversion, cancellation and interactions with existing queue priorities. |
| 13 | **Priority inheritance does not extend to all runtime locks.** `shared_mutex` releases its state mutex while logical readers/writers hold the shared lock, so inheritance cannot reach those owners. Writer preference can starve readers. C++ static initialization waits poll with `osDelay(1)` and do not donate priority. [D, H] | Implement a bounded shared-lock policy and blocking static-guard ownership protocol with appropriate priority handling. Reduces inversion and tick-based initialization delays. | Low-priority owners under medium-priority load, writer bursts, multiple readers, recursive initialization and constructor failure. |
| 14 | **Thread teardown support is limited to runtime-managed paths.** The Lean worker wrapper runs finalizers and frees platform TLS; arbitrary foreign RTX thread exit does not automatically invoke this sequence. Nontrivial C++ `thread_local` destructor registration is not provided. [C, D, F, I] | Add a runtime-owned foreign-thread lifecycle adapter and, separately, a C++ TLS destructor registry if that capability is required. Prevents lifecycle leaks and broadens C++ FFI compatibility. | Thread exit/ID reuse, destructor/finalizer order, repeated creation and exception state cleanup with both toolchains. |
| 15 | **Resource failure handling depends on library infrastructure and is inconsistent.** Lean OOM prints/exits, `cmsis_fail` prints/flushes/aborts, and C++ allocation may throw. Worker/task execution has no general boundary translating escaping C++ exceptions into a defined runtime result. [C, D, E, F] | Centralize a minimal failure hook and specify exception containment at task/FFI boundaries. Enables predictable failure reporting/termination without requiring a functioning heap or stdio lock. | Heap/RTX exhaustion, locked or unavailable output, constructor failure and exceptions escaping task callbacks; cleanup where recovery is supported. |
| 16 | **Lean small objects inherit general-heap overhead.** `lean_alloc_small_object` uses malloc plus a separate size word (four bytes on this target), in addition to Lean and allocator metadata. [E, G] | Add a Lean-owned size-class pool behind small-object allocation/free, preserving the object ABI and leaving libc/C++ allocators unchanged. Can reduce object overhead, fragmentation and allocation latency for that subset. | Alignment, size metadata, pooled/fallback allocation pairing, cross-thread free and exhaustion; preserve heartbeat accounting. |
| 17 | **Software stack accounting uses a sampled frame rather than actual thread bounds.** `save_stack_info()` subtracts the full configured stack size from its current frame, omitting stack already consumed before sampling. CMSIS `stack_guard` is empty, and software detection depends on explicit `check_stack()` calls. [C, F] | Base thresholds on actual thread stack bounds and add integrated overflow detection. Corrects available-space accounting and improves detection coverage. | First checks at different call depths, worker/foreign-thread entry, recursion and overflow detection before memory corruption. |

### Very high

| # | Current runtime limitation | Proposed runtime change and benefit | Tests needed |
| --- | --- | --- | --- |
| 18 | **The runtime cannot currently be compiled exception-free by changing flags alone.** `lean_unreachable`, stack/heartbeat/interrupt checks and C++ allocation paths depend on exceptions. The smoke suite also explicitly tests them. [B, F, G] | Add an exception-free runtime variant with defined replacements for Lean throwing paths and a compatible supplied C++ library variant. Standard-library implementations remain unchanged; an unavailable compatible variant is a constraint. Potentially removes unwind/exception-only code while keeping Lean `Except`/`IO.Error` values. | Upstream and FFI compatibility, allocation/stack/heartbeat failures, constructors and tasks; compare the exception-enabled variant. |
| 19 | **The current embedded profile always includes multithreaded runtime infrastructure.** `LEAN_MULTI_THREAD` and the CMSIS backend are selected unconditionally; there is no verified reduced-capability profile omitting scheduler/TLS integration. [A, C, D, E] | Provide a separately validated single-thread runtime variant with specified task/promise semantics. Potentially removes worker, TLS and synchronization dependencies. | Module initialization, task/promise behavior, references, finalizers and FFI against that variant's defined contract. |
| 20 | **Reference counting has unbounded work at individual runtime calls.** A final `lean_dec` iteratively traverses and frees the newly unreachable graph, including external finalizers. Cross-thread publication through `mark_mt` also traverses reachable objects. [E] | Add budgeted/deferred reclamation and investigate incremental publication where semantics permit. Reduces worst-case runtime pauses, with additional retained memory and changed destruction timing. | Ownership/lifetime differential tests, finalizer order, peak memory and cross-thread publication races. |
| 21 | **The 32-bit object ABI imposes allocation on boxed fixed-width scalars.** `lean_box_uint32`, `lean_box_uint64`, `lean_box_float` and `lean_box_float32` allocate constructors. `Nat` uses only 31 immediate bits: the existing `Nat` nanosecond clock result allocates after roughly 2.15 seconds of uptime. [D, G] | Add allocation-free native runtime interfaces where possible; broader unboxed representations require compiler/runtime coordination. Can reduce allocation/refcount traffic, but is not generally a runtime-only ABI substitution. | Generated-code/FFI compatibility, polymorphic containers, boxing/unboxing, scalar boundaries and ownership. ABI-wide changes require broad compiler/runtime differential tests. |

## Standard-library constraints and compiler-specific choice

**Scope:** libc and C++ standard-library implementations remain unmodified. Library-internal allocator, stdio, reentrancy and unwinder changes are excluded from the runtime proposals. The options here are selecting a supplied library/variant and adapting this repository's startup, TLS and retargeting interfaces. No standard-library source patches are proposed. A different unmodified library may require matching C++ binaries and changes to this port; supplied, integrated variants are preferable to minimize that work.

### Documented constraints, with no library fix proposed

| Constraint | Current evidence and consequence |
| --- | --- |
| IRQ-masked library operations | Repository hooks in `cmsis_libc.cpp` route all retargetable locks to the nested PRIMASK allocator lock in `cmsis_tls.cpp`; GCC file locks do likewise. This is a port integration choice, not evidence of a libc defect. The resulting IRQ latency depends on the library operation. It is recorded here without a proposed libc repair; switching libraries alone does not remove these hooks. |
| GCC reentrancy state | Current newlib integration retains shared reentrancy state/`errno`. Serializing operations does not preserve independent per-thread error state. No newlib implementation change is proposed; the present integration remains a documented constraint. Picolibc's compiler TLS model is an alternative when supplied in a compatible toolchain. [I, L2] |
| General-purpose allocation | The supplied libc allocator's fragmentation, metadata and execution time remain external constraints. Runtime-owned object pools can bypass some calls, but are not a proposal to replace or modify libc `malloc`/`free`. |
| C++ support remains a separate dependency | Changing libc does not automatically remove `libstdc++`/`libc++`, exception support or the unwinder. Selection must preserve a compatible complete C/C++ runtime combination. [L1] |

### Recommended choice for each configured compiler

Recommendations prioritize the current runtime's required C++ exceptions, RTX integration and supported console behavior, without modifying standard libraries. They are compatibility recommendations; a smallest/fastest winner requires equivalent firmware measurements.

| Compiler | Recommended choice | Alternatives assessed and conclusion | Change risk |
| --- | --- | --- | --- |
| **Arm GNU GCC 14.3.1** (`Corstone300-GCC`, `DevKit-E8`) | **Retain supplied full newlib + exception-capable libstdc++/libsupc++ for the current profile.** | **Newlib-nano** is the first supplied size-oriented alternative to evaluate, especially for a future exception-free profile. The installed `nano.specs` changes headers and remaps both C and C++ libraries to nano variants; nano C++ exception support is not established for this installed release. An explicitly supported nano-C/exception-capable-C++ combination could improve size without losing current behavior. **Picolibc** offers a more suitable TLS model, but this GCC setup does not select/provide an integrated picolibc configuration: prefer a compatible preintegrated distribution including its C++ libraries; integrating unmodified upstream libraries separately is a higher-risk option. **LLVM libc** has no verified supplied GCC integration here and is not recommended for this configuration. [L1, L2, L3] | Keeping the baseline: none. Supplied nano selection: **moderate/high**, depending on C++ compatibility. Different integrated libc/toolchain distribution: **high**. |
| **ATfE Clang 23.1.0** (`Corstone300-CLANG`) | **Retain supplied picolibc + matching libc++/libc++abi.** This is already the project's embedded-library choice, with native libc TLS supported by the port. | **LLVM libc** is the strongest alternative to evaluate: ATfE 23.1.0 supplies a selection path, and Arm identifies it as the future default. Its release documentation still describes partial C API coverage and restricted C++ file IO. This port uses `sys/lock.h`, `unistd.h`, `fileno`/`isatty`, custom heap/startup symbols and semihosting, so migration requires an API/retargeting audit. No size/performance advantage is established here. **Newlib/newlib-nano** overlays exist, but ATfE documents newlib support as experimental; they offer no demonstrated advantage over the current picolibc integration. [L1, L4, L5] | Keeping picolibc: none. LLVM libc integration: **high**. Newlib overlays: **high**, without a current reason to prefer them. |

**GCC nano qualification:** the installed toolchain contains `libc_nano.a`, `libstdc++_nano.a`, `libsupc++_nano.a` and `nano.specs`. The inspected specs explicitly rewrite `-lstdc++` and `-lsupc++`; this is not a libc-only switch. Arm's original nano description documents exception-disabled library builds, but that historical description does not prove the exact configuration of 14.3.1. Therefore nano is a conditional optimization candidate, not a validated replacement for the current exception-enabled runtime. This requires vendor configuration evidence and exception regression tests, not a standard-library modification. [L3]

**Picolibc qualification:** compiler TLS can reduce per-thread state to the variables actually linked, but the RTOS still needs correct TLS initialization and switching. Picolibc also retains locking requirements. Its selection does not resolve the runtime's own IRQ-masked TLS registry or scheduling limitations. The native-TLS path is currently guarded by __clang__, so GCC+picolibc would also need an explicit library-backend selection and matching TLS support in this port. [L2, L6]

For any library change, the decisive checks are the existing minimal/console suites, typed C++ catches and allocation failures, per-thread `errno`/TLS, static guards, heap alignment, FVP semihosting and the applicable board UART. Compare ROM, live RAM, allocation throughput and maximum IRQ masking with identical runtime features. GCC-versus-Clang footprint differences cannot be attributed to libc alone.
